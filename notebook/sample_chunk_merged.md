# Langraph
Langraph is a Python library for building graph-based conversational AI workflows. The course scope: design, implement and manage dialogue systems using a graph approach; step-by-step, beginner-friendly, with exercises and example answers on GitHub.

## Type annotations
- Rationale
  - Type annotations are used extensively in Langraph to define state schemas and to provide type safety, improve readability, and make debugging easier.
- Dictionary vs type dictionary
  - Regular Python dicts are flexible but do not enforce structure or types, which can lead to runtime logical errors in large projects.
  - A type dictionary is implemented as a class (a typed dictionary) where each key has an explicit type annotation (e.g., name: str, year: int). Benefits: type safety and clearer debugging.
- Union
  - Union specifies that a value may be one of several types (example: x: Union[int, float]). Used broadly in Langchain and Langraph to allow flexible but constrained inputs and to provide type hints that help catch incorrect usage.
- Optional
  - Optional[T] indicates a value may be either T or None. Example: name: Optional[str] — the function must accept either a string or None and treat None explicitly.
- Any
  - Any means the value may be any data type; use when no type restriction is required.
- Lambda functions
  - Short inline functions used for small transformations (examples: squaring a value, mapping with lambda x: x * x). Lambdas are concise alternatives to simple loops for small operations.

# Core elements in Langraph
## State
- Shared data structure that holds the current application context (the application's memory).
- Nodes read from and write to the state as they execute.
- Analogy: the whiteboard in a meeting room where participants record and update information.

## Node
- An individual function or operation that performs a specific task within the graph.
- Receives input (often the state), processes it, and returns an updated state.
- Analogy: an assembly-line station that performs one job (attach, paint, inspect, etc.).

## Graph
- The overarching structure that maps how nodes are connected and executed; represents workflow sequence and conditionals.
- Analogy: a road map showing routes and intersections (choices) between cities.

## Edges
- Connections between nodes that determine execution flow (which node runs next).
- Analogy: train tracks connecting stations; the state moves along edges.

## Conditional edge
- A specialized connection that chooses the next node based on a condition evaluated against the state (like an if/else). Analogy: a traffic light deciding direction.

## Start point (start node)
- A virtual entry point that marks where graph execution begins; does not perform operations itself. Analogy: the starting line of a race.

## End node
- Signifies workflow conclusion; when reached, execution stops. Analogy: the finish line.

## Tools
- Specialized utilities nodes use (e.g., fetch data from an API). Tools provide functionalities used by nodes but are not nodes themselves. Analogy: tools in a toolbox (hammer, screwdriver).

## Tool node
- A node whose primary job is to run a tool and place the tool output back into state so other nodes can use it. Analogy: an assembly line operator running a machine.

## State graph
- Framework object that builds and compiles the graph structure, manages nodes, edges, and overall state flow. Analogy: a blueprint for a building outlining connections and design.

## Runnable
- A standardized executable component inside Langraph; a building block that can represent various operations. Analogy: Lego bricks snapped together to build larger structures.

## Message types (common)
- Human message: represents input from a user.
- AI message: represents responses generated by AI models.
- System message: provides instructions or context to the model.
- Tool message: represents output from a tool (or function call) used by nodes.
- Function message: function/tool call messages (used when calling external functions or tools).

# Building graphs in Langraph — general workflow
- Define a typed state schema using a class typed as a type dictionary.
- Implement node functions: each node takes the state (the typed state) and returns the updated state.
- Write meaningful docstrings for nodes; they describe node behavior and are used by LLMs in later agent builds.
- Create a StateGraph with the state schema: graph = StateGraph(agent_state).
- Add nodes: graph.add_node(name, action_function) — action_function is the node function.
- Set entry and finish points: graph.set_entry_point(node_name), graph.set_finish_point(node_name) or use start/end imports.
- Add edges between nodes: graph.add_edge(start_node, end_node).
- For conditional routing, use graph.add_conditional_edge with a source node, routing function, and a path_map that maps edge names to target nodes.
- Compile: app = graph.compile(). Compilation validates structure but does not guarantee logical correctness.
- Invoke execution: app.invoke({...}) with structured inputs matching the state schema.
- Debugging tips: print state before/after node execution to inspect updates; watch for inadvertently overwriting state keys (concatenate when you mean to preserve previous content).

# Graph 1 — Hello World Graph
- Objectives: define agent state structure, create a greeting node, compile and invoke a minimal graph to understand single-node data flow.
- Agent state schema: class AgentState(TypeDict): message: str
- Greeting node (greeting_node):
  - Docstring: describes that it adds a greeting to state.message.
  - Action: update state.message by concatenating a greeting (e.g., "hey " + state.message + " how is your day going") and return state.
- Graph construction:
  - graph = StateGraph(agent_state)
  - graph.add_node("greeter", greeting_node)
  - graph.set_entry_point("greeter")
  - graph.set_finish_point("greeter")
  - app = graph.compile()
- Invocation example: result = app.invoke({"message": "Bob"}) yields "hey Bob how's your day going".
- Exercise: build a personalized compliment agent that concatenates the compliment rather than replacing state.

# Graph 2 — Multiple inputs and list processing
- Objectives: handle multiple inputs and list data in a single node.
- Agent state schema: values: List[int], name: str, result: str
- process_values node:
  - Sum the list: total = sum(state.values)
  - Concatenate into result: state.result = f"Hi there {state.name}. Your sum is equal to {total}"
  - Return state.
- Graph construction: add node (e.g., "processor"), set entry/finish, compile, and invoke using the compiled app (important: invoke app, not graph object before compile).
- Debugging and caveats:
  - Print state before/after node action to visualize updates.
  - Fields not provided as inputs may be initialized to None; avoid reading None values before assignment.
- Exercise: single-node operation that, given a list and an operation string ("plus" or "times"), either adds or multiplies elements and returns a formatted message.

# Graph 3 — Sequential graph (multiple nodes)
- Objectives: create and connect multiple nodes that sequentially process and update the state.
- Agent state schema: name: str, age: str, final: str
- Node design:
  - first_node: sets state.final = f"hi {state.name}"
  - second_node: appends age info; important to concatenate (state.final = state.final + " you are ...") rather than overwrite to preserve earlier content.
- Graph construction:
  - Add both nodes to graph.
  - Connect first_node -> second_node via graph.add_edge("first_node","second_node").
  - Set entry to first_node and finish to second_node, compile and invoke.
- Conceptual notes: edges are directed; state keys can be updated by any node multiple times.
- Exercise: extend to three nodes: greeting, age description, skills formatting; combine outputs into a final message.

# Graph 4 — Conditional graph
- Objectives: implement conditional routing in the graph (choose different next nodes based on state).
- Agent state schema: number1: int, operation: str ("+" or "-"), number2: int, final_number: int
- Nodes:
  - adder: state.final_number = state.number1 + state.number2; return state.
  - subtractor: state.final_number = state.number1 - state.number2; return state.
  - decide_next_node (router): inspects state.operation and returns an edge identifier string (e.g., "addition_operation" or "subtraction_operation"). Important: this node returns an edge identifier rather than a modified state.
- Important Langraph detail: if a node returns an edge (instead of a state), adding the node to the graph requires an action that returns a state (even if it does not change it). Use a pass-through lambda to satisfy the signature when adding the router node, e.g. lambda state: state.
- Graph construction:
  - Add nodes including router.
  - Connect start -> router.
  - Use graph.add_conditional_edge to map router paths to edge names and destination nodes (path_map maps "addition_operation" -> add_node, "subtraction_operation" -> subtract_node).
  - Connect add_node and subtract_node to the end node, compile and invoke.
- Invocation example: number1=10 operation="-" number2=5 => final_number=5.
- Exercise: duplicate the structure to process two pairs of numbers (two operations and two results).

# Graph 5 — Looping graph
- Objectives: implement looping logic to route flow back to nodes until a condition is met.
- Example design (five random numbers):
  - Agent state: name: str, numbers: List[int], counter: int
  - greeting_node: writes a greeting into state.name and initializes state.counter to 0 (robustness: reset counter irrespective of input to avoid unexpected iteration counts).
  - random_node: append a random integer to state.numbers, increment state.counter by 1, return state.
  - should_continue router: if state.counter < 5 return the loop edge; else return exit edge. (Router returns edge names.)
- Graph construction:
  - Connect start -> greeting_node -> random_node.
  - Add conditional edge from random_node (or router) using should_continue as the routing function; path_map routes loop -> random_node and exit -> end.
  - Compile and invoke; prints show the state evolving and the counter incrementing until the loop exits.
- Key implementation detail: there are multiple ways to implement loops; this example routes via conditional edges rather than using an internal for-loop inside a node.
- Exercise: implement an autonomous higher-or-lower guessing graph that repeatedly guesses a number between bounds (default 1–20), adjusts bounds based on hints (higher/lower), stops on correct guess or after a max attempts limit (7). Inputs: player name, empty guesses list, attempts=0, lower_bound=1, upper_bound=20.

# AI agents — integrating LLMs into graphs
- Langraph workflows commonly integrate Langchain's LLM wrappers (e.g., ChatOpenAI). Env files (loaded with load_dotenv) store API keys.
- General pattern: construct state schema containing message objects, implement a node that calls the LLM via lm.invoke(messages), append the LLM response to state, and return the state. Use the compiled graph for invocation.

## Simple bot (basic LLM wrapper)
- Agent state: messages: List[HumanMessage]
- Initialize LLM: ChatOpenAI(model=...) (transcript referenced the "GPD40 model").
- process node: call lm.invoke(input=state.messages) to get a response, print response content, return state.
- Graph: single node sandwiched between start and finish; compile and run a simple loop to accept user input and call app.invoke.
- Limitation: no persistent memory across program restarts — state is in-memory and lost when the process ends.

## Memory agent (conversation history)
- Goal: enable the agent to remember earlier messages during a session and persist conversation across runs.
- Agent state: messages: List[Union[HumanMessage, AIMessage]] — use Union to allow human and AI messages in the same list.
- Interaction loop:
  - Append HumanMessage(content=user_input) to state.messages.
  - Invoke the compiled graph which sends the entire state.messages history to the LLM so it can respond with context.
  - After lm.invoke, append AIMessage(content=response.content) to state.messages.
  - Print response.
- Persistence across program runs:
  - Save conversation history to an external file (simple approach): iterate conversation_history and write each entry to a log file distinguishing user vs AI messages.
  - This keeps the conversation outside program variables so it survives process exit.
- Cost and token growth problem:
  - Conversation history grows with every exchange, increasing token usage and cost.
  - Simple mitigation: prune older messages when the history exceeds a threshold (e.g., remove earliest messages when length > N) to limit token consumption while preserving recent context.

## React agent (reasoning and acting) — introduction & foundations
- Purpose: a React agent reasons and acts in a loop, choosing tools to call and deciding when no more tool calls are required before finishing.
- Architecture: start -> agent node (loops) -> tool calls (one or many) -> agent decides next action -> eventually route to end.
- Important imports and concepts introduced for building React agents:
  - Annotated (type annotation): allows attaching metadata to a type without changing the underlying type (useful for constraints like "must be a valid email format"). Metadata is accessible via .__metadata__ or similar inspection.
  - Sequence (type annotation): simplifies handling sequence updates (e.g., appending messages) by automating sequence-state update behavior and avoiding manual list manipulation inside nodes.
  - BaseMessage / ToolMessage / SystemMessage:
    - BaseMessage: foundational parent class for all message types in Langraph.
    - SystemMessage: provides instructions/context to the LLM (e.g., "you are a helpful assistant").
    - ToolMessage: carries tool call outputs and identifiers back to the LLM as part of the message stream.
  - Tools & ToolNode: create callable tools and nodes whose main job is to run tools; tools supply external capabilities for the agent.
  - Reducer functions (add_messages): control how node updates merge into existing state. add_messages is a reducer that aggregates/ appends new messages into the state instead of overwriting it; this prevents accidental replacement of conversation history when multiple nodes or tool calls update the state.
- Practical note: use add_messages (or other reducers) to ensure new messages accumulate properly in message lists when multiple nodes or tool calls update the state.

## React agent (reasoning and acting) — additional practical behaviors
- Tool decorator docstring requirement
  - Every function registered as a tool must include a docstring describing the tool. If a tool lacks a docstring (or description), the graph will raise an error during execution.
  - The docstring is used to inform the LLM what the tool does; omitting it prevents the graph from working correctly.
- Tool-call behavior observed during execution
  - The LLM decides which tool to call and what arguments to pass to each tool.
  - Multiple tool calls can occur in a single agent invocation; repeated tool calls indicate the agent routed through the tool node multiple times (loop via conditional edges).
  - Tool-call counts expose whether the LLM relied on external tools for factual computation (e.g., arithmetic) rather than producing an approximate answer from its internal training data.
  - The agent may choose not to call any tool if the LLM determines no tool is necessary; the agent can still produce a final response without tool usage (e.g., returning a joke).

## Drafter — mini-project (agentic drafting system)
### Objectives and requirements
- Speed up drafting of documents and emails.
- Human–AI collaboration: human provides continuous feedback; the agent updates drafts iteratively and stops when the human is satisfied.
- Fast operation and the ability to save drafts to disk.

### Architecture decisions
- Graph topology: start -> agent -> tools -> end.
- Important deviation from a React agent: the save tool must terminate the process directly (tools -> end) instead of routing back to the agent. Update tool calls should route back to the agent to continue the collaborative loop.

### Implementation notes and workarounds
- Injected state exists in Langraph for passing state into tools, but it was not used here (beyond the course scope). A global variable is used as a practical workaround:
  - Tools update the global document content variable.
  - The save tool reads the global variable to write the text file.
- Agent state schema uses the same typed pattern as earlier examples:
  - messages: Annotated[Sequence[BaseMessage], Reducer(add_messages)] — sequence metadata plus add_messages reducer to append messages rather than overwrite.

### Tools
- Update tool
  - Signature: update(content: str)
  - Docstring: describes that it updates the document with provided content.
  - Behavior: marks the global document content variable with the new content and returns a confirmation message (e.g., "document has been updated successfully; current content is ...").
- Save tool
  - Signature: save(file_name: str)
  - Docstring: states it saves the current document to a text file and finishes the process.
  - Behavior:
    - Ensures the filename ends with .txt; appends .txt if missing.
    - Reads the global document content and writes it to the specified text file.
    - Includes try/except to surface file-write errors for debugging.
    - Returns a confirmation message including the saved filename.
- Tools list: [update, save]
- Bind tools to the LLM with model.bind_tools(tools).

### Agent node (r_agent)
- System prompt: instructs the LLM that it is "Drafter," a writing assistant that will use update/save tools, must always display current document after modifications, and follow a human-in-the-loop workflow.
- Interaction logic (robustness measures):
  - If state.messages is empty: prompt the user with an introductory question (e.g., "I'm ready to help you update a document. What would you like to create?") and store the response as a HumanMessage.
  - If state.messages is non-empty: ask the user "What would you like to do with the document?" and print the current document content to the terminal for context; store the user input as a HumanMessage.
- Invocation: combine system prompt, state messages, and the new user message, then call model.invoke(...) and allow the add_messages reducer to append outputs to state.messages. Return the updated state.
- Terminal formatting: additional helper print functions are used to render AI responses and tool messages prettily (purely display logic, not Langraph-specific).

### Conditional routing (should_continue)
- Purpose: choose between continue (loop back to agent) or end (terminate) after a tool call.
- Logic:
  - If no messages exist, default to continue (robustness).
  - Inspect the most recent tool message to determine which tool was used.
  - If the save tool was used -> return the end edge (terminate the graph).
  - If the update tool was used -> return the continue edge (route back to agent for further edits).

### Graph construction
- Nodes: agent (r_agent) and tools (ToolNode wrapping update & save).
- Entry point: agent.
- Edges:
  - Directed edge agent -> tools (agent invokes tool node when appropriate).
  - Conditional edge from tools -> {continue: agent, end: finish}, where continue uses the update tool path and end uses the save tool path.
- Compile the graph to produce the runnable app.

### Runtime behavior and examples
- Interactive usage: run python drafter.py; agent prompts; user issues drafting instructions; agent uses update tool(s) to modify the global document and displays updates.
- The agent can generate a suitable filename itself when saving; the save tool writes the .txt file and returns the saved filename.
- The saved file contents should match the final document content printed during the session.
- The system supports starting from an empty document or from an existing document by populating the initial messages list before invoking the graph.

### Suggested extensions (non-mandatory)
- Add voice input/output (e.g., OpenAI Whisper for STT, ElevenLabs for TTS).
- Provide a GUI for easier editing.
- Integrate a knowledge base for contextual drafting.

## Retrieval augmented generation (RAG) agent
### Architecture overview
- Graph topology: start -> LLM agent -> (if tool call) retriever agent -> loop back to LLM agent -> ... -> end.
- Two distinct agents:
  - Retriever agent: executes retrieval tool calls and returns document-context results.
  - LLM agent (main): produces tool-call decisions and final answers, consuming retrieved context when available.
- Conditional routing controls the loop (continue when a tool call was produced; end when no tool call is required).

### LLM and embedding model notes
- Set model temperature for desired determinism; temperature=0 yields deterministic outputs.
- Embedding model must be compatible with the LLM and vector store (e.g., matching expected vector dimensions and model compatibility).

### Document loading and chunking
- Use a PDF loader (PyPDFLoader) to load the PDF and count pages; verify file exists and report page count.
- Chunking parameters:
  - chunk_size (e.g., 1000 tokens) — size threshold for creating a new chunk.
  - chunk_overlap (e.g., 200 tokens) — number of tokens duplicated between consecutive chunks to preserve context across chunk boundaries.
  - Use a RecursiveCharacterTextSplitter (or equivalent) to produce chunks from the document pages.

### Vector store (Chroma)
- Create a Chroma vector database to store embeddings.
- Specify storage path and collection name (example: collection name = "stock_market").
- If collection does not exist, create it and persist embeddings to the chosen directory (chroma creates local files such as .bin files).
- Wrap chunked documents with an embedding model and persist them into the Chroma collection.

### Retriever
- Instantiate a retriever from the vector store.
- Set search_type (similarity) and k (number of top chunks to return); example k=5 (returns top 5 relevant chunks).

### Retriever tool implementation
- Tool signature: retriever_tool(query: str) -> str
- Behavior:
  - Query the retriever for the top-k similar chunks.
  - If no relevant chunks are found, return a string indicating no relevant information was found.
  - If relevant chunks exist, aggregate them into a string (or structured list) and return those results to the calling agent.
- Bind the retriever tool to the LLM.

### System prompt and hallucination mitigation
- Provide an explicit system prompt instructing the LLM to answer questions about the loaded document.
- Instruct the LLM to always cite specific parts of the document used in answers to reduce hallucination risk.

### Retriever agent (tool executor)
- The retriever agent inspects the LLM response for tool call instructions.
- If a valid tool name is present (retriever_tool), the agent invokes the tool with the provided arguments and returns the tool output into state.
- If the LLM requested an invalid tool name, return an error-like message asking to select from the available tools.

### Graph construction
- Nodes: llm_agent (main LLM) and retriever_agent (tool executor).
- Conditional edge function (should_continue) inspects whether the latest LLM output contains a tool call; if yes -> invoke retriever_agent; otherwise -> finish and present final answer.
- Compile the graph into a runnable app.

### Testing and verification
- Running the script should:
  - Load the PDF and report the page count (example: 9 pages).
  - Create the Chroma vector store and persist embeddings (local files appear in the specified directory).
- Example query flow:
  - User asks: "How was the S&P 500 performing in 2024?"
  - LLM issues a retriever tool call with the query.
  - Retriever returns the most similar chunks (k=5) to the LLM.
  - LLM responds with an answer and cites document passages.
- Verification example: cited facts (e.g., total return ~25%) can be checked against the original PDF text returned by the retriever; the system should avoid hallucination for queries not present in the document (e.g., "How did OpenAI perform in 2024?") by returning that the document contains no relevant information.
