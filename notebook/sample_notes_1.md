# Type annotations

## Dictionaries

- Regular Python dict:
  - Flexible, efficient key-based retrieval.
  - Problem: no enforcement of structure or data types → source of logical errors in larger projects.

## Typed dictionary (TypedDict)

- Implemented as a class that specifies keys and their data types.
- Example pattern:
  - class AgentState(TypedDict):
      name: str
      year: int
- Benefits:
  - Type safety: explicit types reduce runtime errors.
  - Improved readability and easier debugging.
- Usage note:
  - TypedDicts are used extensively in Langraph to define states.

## Union

- Union defines that a value may be one of several types.
- Example: a function that squares x where x: Union[int, float].
  - Passing int or float works; passing a string fails.
- Used extensively in Lang Chain and Langraph to provide flexible type safety.

## Optional

- Optional[T] is equivalent to Union[T, None].
- Example: def nice_message(name: Optional[str]) → name may be a str or None.
  - If name is None, code can branch to a default behavior.
- Enforces that only the specified types (e.g., str or None) are allowed.

## Any

- Any allows any data type.
- Example: def print_value(x: Any) → accepts and prints any value.

## Lambda functions

- Short inline functions used to write concise transformations.
- Example 1: square function as a normal def.
- Example 2: map with lambda to square each number in a list:
  - list(map(lambda x: x * x, nums)) → [1, 4, 9, 16]
- Useful for short, efficient operations compared to verbose loops.

# Langraph core elements

## State

- Shared data structure holding current information/context of the entire application.
- Analogy: a whiteboard in a meeting that all participants (nodes) can read and update.
- Stores variables that nodes access and modify during execution.

## Node

- Individual functions or operations that perform specific tasks within the graph.
- Each node:
  - Receives an input (often the current state).
  - Processes it.
  - Produces an output or updated state.
- Analogy: assembly line station performing one specific job.

## Graph

- Overarching structure that maps how tasks (nodes) are connected and executed.
- Represents workflow sequence and conditional branching.
- Analogy: road map showing routes and intersections.

## Edges

- Connections between nodes that determine execution flow.
- Edges indicate which node executes next after the current node completes.
- Analogy: train tracks connecting stations; the state is the train moving along.
- Conditional edge:
  - Specialized connection that chooses the next node based on conditions evaluated on the state.
  - Analogy: traffic light deciding which path to take (if/else semantics).

## Start point (start node)

- Virtual entry point marking where workflow execution begins.
- Does not perform operations itself.
- Analogy: starting line of a race.

## End point (finish node)

- Signifies conclusion of workflow; reaching it stops graph execution.
- Analogy: finish line of a race.

## Tools

- Specialized functions or utilities that nodes can call to perform tasks (e.g., fetching data from an API).
- Tools enhance node capabilities.
- Analogy: tools in a toolbox (hammer, screwdriver).

## Tool node

- A special node whose primary job is to run a tool and return the tool's output into the state.
- Analogy: assembly line operator controlling a machine (tool) and sending results back into the line.

## StateGraph

- Component that builds and compiles the graph structure.
- Manages nodes, edges, and overall state flow.
- Analogy: blueprint of a building outlining design and connections.

## Runnable

- Standardized executable component in Langraph that performs a specific task.
- Can represent various operations; analogous to a Lego brick that can be snapped together with others to form complex workflows.
- Difference between runnable and node:
  - Runnable: generalized executable building block.
  - Node: typically receives a state, performs an action, and updates the state.

## Message types (common)

- HumanMessage: input from a user.
- AIMessage: responses generated by AI models.
- SystemMessage: instructions or context provided to the model.
- ToolMessage: message specific to tool usage (similar to a function message).
- Function/FunctionMessage: represents a tool or function call.

# Coding with Langraph — practical graphs

Note: examples follow patterns used when coding Langraph graphs: define a TypedDict for the state, implement node functions that accept and return that state, build the StateGraph, add nodes, set entry/finish points or edges, compile the graph, then invoke it.

## Hello World graph — single-node flow

Objectives:

- Define agent state schema.
- Create a simple node that updates state.
- Build, compile, and invoke a basic graph.
- Understand data flow through a single node.

Key implementation steps (conceptual):

- Imports: dict, TypedDict, StateGraph.
- Define state schema:
  - class AgentState(TypedDict):
      message: str
- Node definition pattern:
  - def greeting_node(state: AgentState) -> AgentState:
      """Simple node that adds a greeting message to the state."""
      state['message'] = "hey " + state['message'] + " how is your day going"
      return state
- Docstrings:
  - Important habit: docstrings describe the node's action; useful when LLMs later inspect node behavior.
- Build graph:
  - graph = StateGraph(AgentState)
  - graph.add_node("greeter", greeting_node)
  - graph.set_entry_point("greeter")
  - graph.set_finish_point("greeter")
  - app = graph.compile()
- Invoke:
  - result = app.invoke({"message": "Bob"})
  - Access result['message'] → "hey Bob how's your day going"
- Exercise:
  - Create a personalized compliment agent that concatenates the state rather than replacing it (e.g., "Bob, you're doing an amazing job learning langraph").

## Graph 2 — multiple inputs and list processing

Objectives:

- Define agent state with multiple inputs and types.
- Create a node that processes a list of integers and other fields.
- Build, compile, and invoke the graph; observe state updates.

Key implementation steps:

- Imports: TypedDict, StateGraph, List.
- State schema:
  - class AgentState(TypedDict):
      values: List[int]
      name: str
      result: str
- Node:
  - def process_values(state: AgentState) -> AgentState:
      """Function to handle multiple inputs: sums list and concatenates name into result."""
      state['result'] = f"Hi there {state['name']}. Your sum is equal to {sum(state['values'])}"
      return state
- Build graph:
  - graph = StateGraph(AgentState)
  - graph.add_node("processor", process_values)
  - graph.set_entry_point("processor")
  - graph.set_finish_point("processor")
  - app = graph.compile()
- Invoke example:
  - answers = app.invoke({"values": [1,2,3,4], "name": "Steve"})
  - answers shows values, name, and result ("Hi there Steve. Your sum is equal to 10")
- Debugging print technique:
  - Print state before and after node action to visualize transformation.
- Caveat:
  - If a state attribute (e.g., result) is not passed in, Langraph initializes it as None — avoid using such attributes prior to initialization unless explicitly handled.
- Exercise:
  - Create a graph that accepts a list of integers, a name, and an operation ("+" or "times") and returns either the sum or product of the list in a single node using an if statement.

## Graph 3 — sequential nodes and edges

Objectives:

- Create and connect multiple nodes that sequentially update different parts of state.
- Add directed edge between nodes and observe state evolution through sequence.

Key implementation steps:

- State schema:
  - class AgentState(TypedDict):
      name: str
      age: str
      final: str
- Two nodes:
  - def first_node(state: AgentState) -> AgentState:
      """First node of sequence."""
      state['final'] = f"Hi {state['name']}"
      return state
  - def second_node(state: AgentState) -> AgentState:
      """Second node of sequence."""

    # Important logical detail: concatenate rather than replace

      state['final'] = state['final'] + f" you are {state['age']} years old"
      return state
- Graph construction:
  - graph = StateGraph(AgentState)
  - graph.add_node("first_node", first_node)
  - graph.add_node("second_node", second_node)
  - graph.edge.add_edge("first_node", "second_node")  (use of edge addition)
  - graph.set_entry_point("first_node")
  - graph.set_finish_point("second_node")
  - app = graph.compile()
- Invocation example:
  - result = app.invoke({"name": "Charlie", "age": "20"})
  - result['final'] → "Hi Charlie you are 20 years old"
- Concept reinforced:
  - Nodes can update the same state keys multiple times; to preserve previous content, concatenate instead of overwriting.
- Exercise:
  - Build a three-node sequence: personalize name, format age description, and format a skills list; combine into a final result string.

## Graph 4 — conditional graph (router & conditional edges)

Objectives:

- Implement conditional logic at graph level to route state to different nodes.
- Build router node that selects next node via returned edge identifier.
- Use conditional edges to map router outputs to target nodes.

Key implementation steps:

- Imports: include start and end point helpers (alternative to set_entry_point/set_finish_point).
- State schema:
  - class AgentState(TypedDict):
      number_one: int
      operation: str  # "+" or "-"
      number_two: int
      final_number: int
- Nodes:
  - def adder(state: AgentState) -> AgentState:
      state['final_number'] = state['number_one'] + state['number_two']
      return state
  - def subtractor(state: AgentState) -> AgentState:
      state['final_number'] = state['number_one'] - state['number_two']
      return state
  - def decide_next_node(state: AgentState):
      """Select the next node of the graph by returning an edge identifier."""
      if state['operation'] == "+":
          return "addition_operation"
      else:
          return "subtraction_operation"
    - Note: decide_next_node compares state.operation but does not modify the state → use a pass-through action where required (lambda state: state) so the node returns state when needed by the graph API.
- Graph construction pattern:
  - graph = StateGraph(AgentState)
  - graph.add_node("router", decide_next_node)  (router node)
  - graph.add_node("add_node", adder)
  - graph.add_node("subtract_node", subtractor)
  - graph.add_edge(start, "router")  (connect Start → router)
  - graph.add_conditional_edge(source="router", path=decide_next_node, path_map={
      "addition_operation": ("add_node"),
      "subtraction_operation": ("subtract_node")
    })
  - graph.edge.add_edge("add_node", end)
  - graph.edge.add_edge("subtract_node", end)
  - app = graph.compile()
- Visualization:
  - Start → router
  - router —(addition_operation)→ add_node → end
  - router —(subtraction_operation)→ subtract_node → end
- Invoke example:
  - app.invoke({"number_one": 10, "operation": "-", "number_two": 5}) → final_number = 5
- Exercise:
  - Build a graph that runs two separate conditional computations in parallel (four numbers and two operations) and outputs both results.

## Graph 5 — looping graph

Objectives:

- Implement looping by routing flow back to earlier nodes using conditional edges.
- Create a loop that repeats node execution until a condition is met.

Design (graph to implement):

- Start → greeting_node → random_node
- random_node has a conditional edge:
  - loop edge → random_node (repeat)
  - exit edge → end (stop)
- Generate five random numbers via repeated visits to random_node.

Key implementation steps:

- Imports: random plus usual TypedDict and StateGraph.
- State schema:
  - class AgentState(TypedDict):
      name: str
      number: List[int]
      counter: int
- greeting_node:
  - def greeting_node(state: AgentState) -> AgentState:
      state['name'] = f"Hi there {state['name']}"
      state['counter'] = 0  # initialize/overwrite counter to make flow robust
      return state
  - Rationale: initializing counter avoids unexpected behavior if caller passes a negative or invalid counter.
- random_node:
  - def random_node(state: AgentState) -> AgentState:
      state['number'].append(random.randint(0, 10))
      state['counter'] += 1
      return state
- should_continue (router-like conditional function):
  - def should_continue(state: AgentState):
      if state['counter'] < 5:
          return "loop"
      else:
          return "exit"
- Graph construction:
  - graph = StateGraph(AgentState)
  - graph.add_node("greeting_node", greeting_node)
  - graph.add_node("random_node", random_node)
  - graph.edge.add_edge("greeting_node", "random_node")
  - graph.add_conditional_edge(source="random_node", path=should_continue, path_map={
      "loop": ("random_node"),
      "exit": (end)
    })
  - graph.edge.add_edge("random_node", end)  (exit path)
  - graph.set_entry_point("greeting_node") (or start → greeting_node)
  - app = graph.compile()
- Example invocation:
  - app.invoke({"name": "V", "number": [], "counter": -1})
  - The greeting node overwrites counter to 0 → random_node runs five times → counter reaches 5 → exit → final state contains five random numbers.
- Exercise:
  - Implement an automated higher-or-lower game:
    - System auto-guesses a hidden number between lower bound and upper bound (e.g., 1–20).
    - Max guesses = 7.
    - No human in the loop; graph makes guesses and receives higher/lower hints from a hint node which adjusts bounds.
    - Suggested input state fields: player name, guess list (initialized empty), attempts (0), lower_bound, upper_bound.
    - Hint node must return "higher" or "lower"; graph must adjust bounds accordingly and loop until guessed or attempts exhausted.

## Simple bot (LLM integration)

Objectives:

- Integrate a large language model (ChatOpenAI) into a Langraph node.
- Send and handle messages; build a graph around the LLM call.
- Create a simple conversation loop (without persistent memory).

Key implementation details:

- Imports include:
  - TypedDict, List
  - HumanMessage (from LangChain message types)
  - ChatOpenAI (from langchain.chat_models)
  - StateGraph
  - load_dotenv and environment setup for API key
- State schema:
  - class AgentState(TypedDict):
      messages: List[HumanMessage]
- Initialize model:
  - lm = ChatOpenAI(model_name="gpt-4o")
- Node pattern:
  - def process(state: AgentState) -> AgentState:
      response = lm.invoke(state['messages'])
      print(response)  # or otherwise handle response
      return state
- Graph:
  - graph.add_node("process", process)
  - graph.set_entry_point("process"), set_finish_point("process"), app = graph.compile()
- Interaction loop:
  - Use input() to get a user message, invoke app.invoke with messages list, and loop until user types "exit".
- Observed behavior:
  - LLM works and responds (e.g., "Hello, how can I assist you today?").
  - No memory across runs (data stored in variables/state is lost when the program exits).

## Chatbot with conversation memory

Objectives:

- Maintain conversation history using both HumanMessage and AIMessage types.
- Preserve conversation across multiple turns within a run.
- Persist conversation to a file to survive process restarts.
- Handle history growth considerations.

Key implementation details:

- Imports:
  - HumanMessage, AIMessage
  - Union type annotation (Union[HumanMessage, AIMessage])
- State schema:
  - class AgentState(TypedDict):
      messages: List[Union[HumanMessage, AIMessage]]
  - Union allows the messages list to contain both human and AI message objects.
- Initialize ChatOpenAI as before.
- Node behavior (process):
  - response = lm.invoke(state['messages'])
  - state['messages'].append(AIMessage(content=response.content))
  - print the AI response
  - return state
- Conversation loop:
  - On each user input:
    - Append HumanMessage(content=user_input) to conversation history.
    - Invoke the compiled graph (app.invoke) with the current messages state.
    - After invocation, the AIMessage response was appended by process node.
    - Optionally write conversation history to a log file to persist between runs:
      - Open "log.txt" and write formatted lines for each message in conversation history (mark user as "You", AI as "AI").
- Persisted log example:
  - Saved sequence of human/AI messages as plain text.
- History growth problem:
  - Conversation history grows with every turn; larger history increases token usage and cost.
  - Simple mitigation: trim older messages when history length exceeds a threshold (e.g., > 5 messages), removing oldest messages first to limit token size and cost.

## React agent (reasoning and acting) — introduction and required imports

- React agent pattern:
  - Agent loops, reasons, and chooses tools to call; tools produce outputs which feed back into the agent; agent decides when to stop.
  - Typical structure: Start → Agent node (loop) → Tool calls → Agent decides next action → eventually End.
- Typical imports used for a React agent implementation:
  - Typing: Annotated, Sequence, TypedDict
    - Annotated: attach metadata to a type without changing the base type (e.g., annotated email string with a note "must be valid email format").
    - Sequence: type annotation that helps with state updates for sequences (e.g., chat histories), reduces manual list manipulation in nodes.
  - Environment management: load_dotenv
  - Message classes: BaseMessage, ToolMessage, SystemMessage
    - ToolMessage: conveys tool outputs back to the LLM (includes tool call ID and content).
    - SystemMessage: provides instructions/context to the model (e.g., "You are a helpful assistant").
    - BaseMessage: foundational parent class for all message types (AIMessage, HumanMessage, ToolMessage, SystemMessage inherit from BaseMessage).
  - Chat model: ChatOpenAI
  - Langraph elements: StateGraph, Tool, ToolNode
  - Reducer function: add_messages
    - Reducer functions control how node updates combine with existing state.
    - add_messages aggregates/appends messages instead of overwriting state values.
    - Without a reducer, updates would overwrite existing content.
- Purpose of reducer (add_messages):
  - Ensures new messages are merged into existing state messages, preserving history without accidental replacement.
